# Архитектура проекта PPTX2PNG Bot

## 1. Топология Окружений
* **Production** (`/app/pptx2png/prod`)
* Приватный репозиторий, ветка `main`.
* Боевой токен, живые пользователи.
* **Testing** (`/app/pptx2png/test`)
* Приватный репозиторий, ветка `test`.
* Тестовый токен, интеграционные проверки.
* **Development** (`dev`)
* Публичный репозиторий `pptx2png-public-dev`.
* Открытая песочница без секретов.

## 2. Изоляция и Пути в RAM
* Динамический контекст `ENV_NAME` из папки.
* Файлы и логи хранятся в `/dev/shm`.
* SD-карта Raspberry Pi защищена от износа.
* Базовый путь: `/dev/shm/pptx2png_tasks/{ENV_NAME}`.
* Логи разделены на `bot.log` и `debug.log`.

## 3. Секреты и Безопасность
* `.gitignore` жестко блокирует секретные файлы.
* Скрыты `config.ini`, `allowed_users.txt`, `user_settings.json`.
* База пользователей изолирована от `Path.cwd()`.
* Менеджер инициализируется строго от `SCRIPT_DIR`.

## 4. Компоненты Системы
* **`manage.sh`**
* Управляет фоновыми процессами через `nohup`.
* Использует Bash-массивы против пробелов.
* **`user_manager.py`**
* Персистентное хранилище настроек на JSON.
* Авто-каст ключей `str -> int` для `aiogram`.

## 5. Оптимизированный воркфлоу CI/CD
* Раннер больше не пушит логи в Git.
* Исключены конфликты слияния `dev -> test`.
* Логи выгружаются в Артефакты GitHub.
* Добавлена умная проверка статуса процесса.


Документ описывает структуру, механизмы изоляции сред, конфигурационные уровни и логику автоматизации (CI/CD) бота конвертации презентаций.

Назначение сред:
1. Production (/home/pi/app/pptx2png/prod):
    * Git-связь: Приватный репозиторий, ветка main.
    * Статус: Стабильный бот для конечных пользователей.
    * Токен: Уникальный боевой токен Telegram.
2. Testing (/home/pi/app/pptx2png/test):
    * Git-связь: Приватный репозиторий, ветка test.
    * Статус: Среда интеграционного тестирования перед релизом на прод.
    * Токен: Отдельный токен тестового бота.
3. Development (dev):
    * Git-связь: Публичный репозиторий pptx2png-public-dev, ветка main.
    * Статус: Открытая «песочница» без секретов для работы сторонних ИИ-агентов и проведения ревью через Qodo. Физически переключается внутри каталога ../test.

2. Логика Изоляции и Инициализации Путей
Проект спроектирован так, что процессы prod и test никогда не пересекаются по дескрипторам файлов, логам и кэшу.

Динамическое определение контекста (ENV_NAME)
При старте bot.py вычисляет имя своего родительского каталога:


SCRIPT_DIR = os.path.dirname(os.path.abspath(__file__))
ENV_NAME = os.path.basename(SCRIPT_DIR) # Вернет 'prod' или 'test'

Приоритет путей RAM-диска (SHM_DIR) и Логов (LOG_DIR)
Для защиты физической SD-карты Raspberry Pi от износа, файлы обработки задач и логов разворачиваются в оперативной памяти (/dev/shm). Приоритет выбора путей:
1. Флаги запуска CLI: Аргументы --shm-dir и --log-dir (высший приоритет, передаются из manage.sh).
2. Файл settings.ini: Значения параметров shm_dir и log_dir (если объявлены и не пустые).
3. Поведение по умолчанию (Fallback):
    * SHM_DIR = /dev/shm/pptx2png_tasks/{ENV_NAME}
    * LOG_DIR = /dev/shm/pptx2png_tasks/{ENV_NAME}/logs

Структура каталогов в оперативной памяти (RAM)
/dev/shm/pptx2png_tasks/
├── prod/                             <- Изолированный RAM-диск PROD
│   └── logs/
│       ├── bot.log                   <- Основной лог (INFO+)
│       ├── debug.log                 <- Полный лог отладки (DEBUG+)
│       └── sys_nohup.log             <- Вывод STDOUT самого процесса nohup
└── test/                             <- Изолированный RAM-диск TEST
    └── logs/
        ├── bot.log
        ├── debug.log
        └── sys_nohup.log
3. Разделение Конфигурации и Безопасность
Данные жестко разделены на секретные (запрещенные к публикации) и общие настройки.

Секретные файлы (Заблокированы в .gitignore):
* config.ini: Содержит критические токены (BOT_TOKEN) и ID администратора (ADMIN_ID).
* allowed_users.txt: Локальная база данных белого списка пользователей (ID).
* user_settings.json: Конфигурации параметров конкретных пользователей (качество, выбор формата).

Публичные файлы (Синхронизируются через GitHub):
* settings.ini: Хранит несекретные глобальные лимиты и закомментированные шаблоны путей.

Защита Whitelist и Баз Данных от текущей директории (Path.cwd())
В соответствии с рекомендациями Qodo, инициализация менеджера пользователей привязана исключительно к физическому расположению скрипта, что предотвращает чтение чужих баз данных при случайном вызове утилит из корня ОС:

user_mgr = UserManager(admin_id=ADMIN_ID, base_dir=Path(SCRIPT_DIR))

4. Взаимодействие Скриптов и Функций

Управляющий скрипт manage.sh
Обертка на Bash, использующая безопасные массивы EXTRA_ARGS=(...) для экранирования пробелов в путях.
* Передает боту строгие аргументы: --shm-dir и --log-dir.
* Управляет демонизацией через nohup ... &.
* Реализует команды: start, stop, restart, status, logs, debug-logs, clear-logs.

Менеджер Пользователей user_manager.py (JSON База Данных)
Осуществляет персистентность настроек. При изменении пользователем качества или формата выдачи в Telegram, метод update_user_config мгновенно записывает состояние в user_settings.json.
* Важная особенность: При чтении JSON-файла строковые ключи автоматически преобразуются обратно в int ({int(k): v for k, v in data.items()}), чтобы обеспечивать совместимость со встроенными типами данных ID пользователей в aiogram.



5. Алгоритм Автоматизации CI/CD (GitHub Runner)
Воркфлоу автоматического развертывания .github/workflows/deploy.yml оптимизирован для предотвращения конфликтов слияния и работы с RAM-диском.

[Локальный Push в test] ───► [GitHub Actions] ───► [Self-Hosted Runner на Pi]
                                                           │
   ┌───────────────────────────────────────────────────────┴───────────────────────────────────────────────────────┐
   ▼ (Ветка test)                                                                                                  ▼ (Ветка main)
1. rsync кода в /test/                                                                                          1. rsync кода в /prod/
2. ./manage.sh stop (гасит старый тест)                                                                         2. ./manage.sh restart
3. env RUNNER_TRACKING_ID=0 ./manage.sh start                                                                   3. ./manage.sh status
4. sleep 4 (ожидание инициализации токена)                                                                      
5. Валидация через ./manage.sh status | grep "🟢 Бот РАБОТАЕТ"
6. ЕСЛИ ок: Копирование логов из RAM -> Выгрузка в Артефакты Actions (без коммитов в Git!) -> ./manage.sh stop
7. ЕСЛИ упал: Сбор sys_nohup.log -> Прерывание сборки (exit 1)

Защита от конфликтов Git:
Раннер больше не делает коммитов вида Chore: update debug.log [skip ci] обратно в репозиторий. Все отладочные файлы выгружаются как временные Артефакты сборки (Artifacts) на сервере GitHub, что полностью исключает рассинхронизацию историй при слиянии веток dev -> test.



6. Регламент синхронизации кода между репозиториями
При переносе отлаженных фич из публичной среды ИИ-разработки (dev) в боевую тестовую среду, используется следующий атомарный цикл команд в терминале Raspberry Pi:

# 1. Забираем изменения, подтвержденные ИИ-агентом из публичного репо
git checkout dev
git pull pptx2png-public-origin main

# 2. Переносим изменения в приватный тестовый контур
git checkout test
git pull origin test --no-rebase
git merge dev -m "merge: sync stable dev with test environment"

# 3. Пушим в приватную ветку, триггеря Runner на Raspberry Pi
git push origin test

# 4. Возвращаем папку в режим открытой разработки
git checkout dev
